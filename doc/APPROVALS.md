# 다중 사용자 품질·공정 승인

승인된 사내 구성원이 독립적으로 로그인하여 제출본을 조회하고 검토한다. 공동 편집·채팅·동시 커서 기능은 없다. 업무 기록은 Supabase에 저장하며 승인함은 화면이 활성화된 동안 15초마다, 창 포커스 복귀 및 수동 새로고침 때 갱신한다. WebSocket 푸시 알림은 아니다.

## 절차와 권한

1. 관리자가 가입 신청을 승인하고 **사용자 관리 → 업무 권한 설정**에서 공정 담당과 최종 품질 승인권자를 각각 지정한다. 가입 승인만으로 업무 권한을 주지 않는다.
2. 공정 담당은 **셀 등록·매칭 / 에이징 검사 / 최종검사**로 나눈다. 담당 공정의 확인만 기록할 수 있으며, 확인자 ID·표시명·시각을 보존한다. 팩은 **품질·공정 승인함 → 새 검토 요청**, 공정은 **연구 → 공정 설계·시뮬레이션 → 저장·승인 → 공정 승인 요청**에서 제출한다.
3. 별도로 지정된 최종 품질 승인권자가 고정된 공정 확인 근거를 검토하고 의견과 함께 승인·반려한다. 제출자 또는 해당 제출본의 셀 조합/에이징/최종검사 확인자가 자신의 팩을 최종 검토하는 것은 서버에서 거부한다.
4. 반려 후 검사 또는 개인 배치를 수정하고 새 요청을 제출한다. 이전 제출본과 결정은 보관한다. 대기 중인 본인 요청은 취소할 수 있다.
5. 관리자는 계정·접근·담당 지정 권한만 가진다. 관리자 계정에 공정 확인이나 품질 승인 권한을 부여할 수 없다. 업무 구성원은 복수 공정을 담당하거나 품질 승인 권한을 함께 가질 수 있으나, 자신이 확인한 팩은 다른 승인권자가 검토해야 한다.

| 역할 | 조회 | 제출/본인 요청 취소 | 독립적인 최종 승인·반려 | 담당·승인자 지정 |
| --- | --- | --- | --- | --- |
| 승인된 조회자 | 가능 | 불가 | 불가 | 불가 |
| 업무 권한 미지정 구성원 | 가능 | 불가 | 불가 | 불가 |
| 공정 담당자 | 가능 | 가능 | 불가 | 불가 |
| 최종 품질 승인권자 | 가능 | 공정 담당 겸임 시 가능 | 가능 | 불가 |
| 시스템 관리자 | 가능 | 불가 | 불가 | 가능 |
| 미승인·반려·이용 중지 | 불가 | 불가 | 불가 | 불가 |

승인함에서 갱신할 때 현재 역할도 재확인한다. 클라이언트 화면의 활성 상태와 관계없이 모든 쓰기는 서버에서 현재 승인 상태와 역할을 검사한다. 구성원의 표시명은 제출/처리 당시 값을 보관하여 이후 표시명 변경으로 과거 이력이 바뀌지 않는다.

마이그레이션 004는 기존 관리자의 자동 승인·생산 권한을 제거한다. 기존의 명시적 품질 승인자 지정은 유지하지만 공정 담당은 빈 상태로 시작하므로 관리자가 실제 담당자를 지정해야 한다. 기존 검사/팩 기록의 확인자 이름은 이관 시점의 프로필로 보완하며 과거 제출 스냅샷과 결정은 변경하지 않는다. 가입 반려·이용 중지·조회자 전환 시 업무 권한을 해제한다. 권한 변경은 감사 로그에 남는다.

## 실제 팩 품질

- 셀 조합 확정(호환성을 위해 RPC 이름은 `approve_pack` 유지)과 별도인 품질 판단이다. 매칭 Edge Function과 조합 확정/셀 업로드 RPC는 셀 등록·매칭 담당만 실행할 수 있다. 검사 RPC는 해당 검사 담당만 실행한다. 출하 시스템이나 물리 설비를 자동 제어하지 않는다.
- 구성 셀 8개와 해당 팩 공정 버전의 필수 검사 기록이 있어야 제출할 수 있다. 현재 기본 공정은 모듈 검사·케이싱·최종검사를 사용하며 기존 팩은 당시 에이징·최종검사 기준을 유지한다. 서버가 최신 검사와 셀 측정값을 직접 읽어 제출본을 생성한다. 브라우저가 전달한 검사 결과를 신뢰하지 않는다.
- 검사 불합격 건도 검토 요청할 수 있으나 승인할 수 없으며 반려 후 재검사한다. 승인 시 해당 팩의 필수 공정이 순서대로 완료되고 최신 결과가 모두 합격인지 다시 확인한다.
- 동일 팩은 대기 중 또는 현재 검사본 승인 상태에서 중복 제출할 수 없다. 반려·취소·재검토 필요 상태 후 다시 제출할 수 있다.
- 새 검사 기록이 들어오면 해당 팩의 대기 중 또는 승인 상태를 같은 트랜잭션에서 **재검토 필요**로 변경한다. 이전 승인자·의견·검사 스냅샷은 남고 새 검사 ID가 이벤트에 추가된다. 자동으로 재승인하지 않는다.
- 검사는 `created_at DESC, id DESC`로 최신본을 결정한다. 제출·승인·검사 입력은 동일 팩 행을 잠근다. 승인 시 검사 ID도 재확인한다.

## 공정 계획과 기존 배치 승인

- 개인 브라우저 배치를 명시적으로 제출할 때만 공유한다. 장비 종류·이름·참고 모델명·격자 좌표·방향·처리시간·태그 정의·연결을 복제해 보관하며 합성 센서 스트림·실행 기록은 포함하지 않는다.
- 서버에서 장비/태그 수, 좌표·수치 범위, 중복 ID, 겹침, 순환·분기·합류, 시작/종료 유형과 `source: simulation`을 검증한다. 승인된 실제 장비 연결로 오인하지 않게 한다.
- 같은 제출자의 동일 배치가 대기 중/승인 상태이면 중복 제출을 막는다. 반려·취소 후에는 재제출 가능하다. 변경된 배치는 새 요청으로 제출한다.
- 승인함에서 읽기 전용 3D 미리보기와 장비·태그·연결 표를 확인한다. 승인본은 개인 작업공간으로 복사할 수 있다. 복사본의 편집은 제출본이나 과거 승인을 변경하지 않는다.
- 본인이 제출한 공정은 반려·취소 상태에서도 개인 작업공간으로 복사해 수정할 수 있다. 개인 브라우저 저장본이 없어도 제출 이력에서 수정·재제출을 시작할 수 있다.
- 계획(`Layout.plan`) 포함 공정의 승인은 제출본을 활성 운영 버전으로 등록하며 생산·품질의 신규 팩 기준에 반영한다. 기존 팩의 생성 당시 공정은 유지한다. 계획 없는 이전 가상 배치의 승인은 운영에 반영하지 않는다. 현장 설치·장비 안전 인증·분석 성능 검증과는 별개다. 구현과 서버 배포 절차는 DIGITAL_TWIN.md를 따른다.

## 무결성과 저장

`quality_requests`: 제출 종류·대상·고정 snapshot·요청 사유·현재 상태·제출자/승인자/시각/의견.
`quality_events`: 제출·승인·반려·취소·재검토 필요 이벤트의 추가 전용 이력.

테이블은 RLS로 승인 구성원에게 읽기만 허용하고 직접 INSERT/UPDATE/DELETE를 허용하지 않는다. `submit_quality_request`, `decide_quality_request`, `cancel_quality_request`, `set_quality_reviewer`가 쓰기를 담당한다. [Supabase 함수 권한 지침](https://supabase.com/docs/guides/database/functions)에 따라 보안 정의자 함수의 search_path를 비우고 실행 권한을 제한했다.

승인 시 대상 행을 잠근 후 현재 상태와 제출자를 검사한다. 두 승인자가 동시에 처리해도 첫 결정만 반영하며 다른 요청은 오류 후 새로 조회한다. 팩 잠금 순서는 팩 → 요청으로 통일한다. [PostgreSQL 행 잠금](https://www.postgresql.org/docs/17/explicit-locking.html)을 사용한다. 과거 결정은 덮어쓰거나 편집하는 API를 제공하지 않는다.

일반 회원에게 구성원 전체 이메일/프로필을 추가 공개하지 않는다. 승인 기록에는 당시 표시명과 사용자 ID를 남긴다. 기존 관리자 감사 로그와 별개로 승인 이벤트는 승인된 조회자도 확인할 수 있다.

## 검증과 적용

- 마이그레이션: `202610140003_quality_approvals.sql`.
- `npm test`, `npm run build`, `npm run test:e2e`로 체험 모드의 제출·독립 검토·반려·재검사 재검토·승인 공정 복사와 320~1440px 정렬을 검사한다.
- `node scripts/test-approval-backend.mjs`는 **Supabase 관리 로그인과 네트워크 권한이 필요한 수동 통합 검사**다. 지정 프로젝트에 임시 계정과 임시 셀/팩/요청을 만들며, 두 독립 Chrome 세션의 동시 승인, RLS, 역할 제한, 자기 승인 방지, 직접 쓰기 차단, 불합격 승인 차단, 재검사 무효화, 반려 후 재제출을 검증하고 자신이 만든 기록과 사용자를 삭제한다. 운영 데이터를 삭제하거나 기존 사용자의 역할을 바꾸지 않는다. CI의 기본 테스트에는 포함하지 않는다.
- 체험 모드는 실제 인증을 흉내 내는 역할 선택기를 제공하지만 브라우저 메모리만 사용한다. 실제 모드에는 역할 선택기가 없으며 서버 인증으로만 권한을 판단한다.
