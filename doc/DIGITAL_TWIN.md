# 공정 설계와 작업 효율 시뮬레이션

연구의 공정 설계는 장비·작업 순서·확보 데이터 계획을 정의한다. 시뮬레이션은 목표 수량의 작업시간과 병목을 추정한다. 장비 통신 검수, 합성 센서 관제, 가상 불합격률은 현재 연구 화면에서 제공하지 않는다. 기존 v1 배치 파일과 내부 시뮬레이션 모델은 이전 승인본을 읽기 위해 보존한다.

## 설계와 데이터 확보

장비별 운영 단계, 모델·사양 근거, 위치·방향, 데이터 항목을 정의한다. 데이터 항목을 셀 조합·품질이력·수명·이상징후 분석의 준비 항목과 비교한다. 항목 지정은 실제 장비 지원 확인이나 데이터 수집·AI 학습 실행이 아니다. 샘플링·측정 방법·연결키·실측 품질·라벨은 별도 검증이 필요하다.

초기 6단계는 셀 충방전 검사 → 분류·보관 → 8셀 조합 → 모듈 검사 → 케이싱 → 최종검사다. 추가 장비는 기존 운영 단계에 매핑한다. 운영 반영 시 6단계를 모두 포함하고 순서를 유지한다. 새 검사 종류나 판정 규칙을 임의로 추가하는 기능은 아니다.

## 효율 계산

입력: 목표 1~10000팩, 장비별 자동 처리시간·작업자 투입시간·이동시간(분), 동시 처리 수, 병렬 장비 수. 셀 단위는 8개를 팩 1개분으로 환산하므로 동시 처리 수는 8의 배수다.

단일 작업 경로의 배치 스케줄을 계산한다. 각 단계는 배치 도착과 가장 먼저 비는 장비를 기다린 뒤 자동 시간+작업자 시간을 회당 순차 합산한다. 마지막 미달 배치도 처리한다. 이동시간을 다음 단계 도착에 반영한다. 단계 간 병행 처리가 가능하며 작업자 시간이 전체 완료시간과 동일하지 않다.

출력: 전체 목표 수량 완료시간, 첫 팩 완료시간, 1팩 단독 소요시간, 총 인·분, 기간 평균 처리량, 단계별 대기와 병목 후보. 병목은 정상 처리능력(팩/시간)이 가장 낮은 단계다. 기준안을 고정해 조건과 결과를 비교·내보낸다.

초기 660분·128셀과 조합 14분은 회의·제안 수치를 참고한 예시이며 나머지 조건은 가정이다. 각 장비의 전담 인력이 충분하다고 가정한다. 공유 인력 경합·교대·휴식·고장·재검사·매칭 탈락은 계산하지 않는다. 배치 좌표는 개념도이며 이동시간과 자동 연결되지 않는다. 실측 생산량·수율·안전성을 보증하지 않는다.

## 승인과 운영 버전

`Layout.plan`에 작업·데이터 조건을 저장한다. 서버가 장비 구성과 계획, 6단계 순서를 다시 검증한다. 기존 독립 승인 권한 및 자기 승인 금지를 유지한다.

계획 포함 공정의 승인 트랜잭션에서 `process_releases`에 불변 버전을 등록하고 신규 팩의 운영 기준으로 활성화한다. 동시 승인과 팩 생성은 같은 트랜잭션 잠금으로 순서를 정한다. 반려·취소·개인 수정·기존 plan 없는 승인본은 운영에 적용하지 않는다.

팩 생성 시 활성 설계 ID·제목·전체 설계를 `packs.process_design`에 고정한다. 기존 팩은 NULL 또는 당시 버전을 유지하며 갱신을 거부한다. 생산과 품질은 같은 활성 공정을 조회하고, 선택한 팩 및 검사 화면에서는 해당 팩의 공정과 확보 계획을 표시한다. 추가 측정값을 자동 생성하지 않으며 기존 검사 판정 규칙을 유지한다.

## 배포와 검증

서버 마이그레이션 `202610170001_process_planning.sql`을 웹 배포 전에 적용한다. 마이그레이션 미적용 또는 조회 실패는 운영 공정 조회 오류로 표시하며 승인 연동이 완료됐다고 표시하지 않는다.

검증: `npm test`, `npm run build`, `npm run test:db`, `npx playwright test tests/process-planning.spec.ts tests/twin.spec.ts tests/spatial.spec.ts tests/approvals.spec.ts`. DB 검증은 격리 PGlite PostgreSQL이며 실제 Supabase 배포 검증과 구분한다.
